01 · The problem

A wrong constraint file does not fail. It goes quiet.

Before a chip is built, an engineer writes a timing constraint file. It tells the analysis tools what the design is supposed to do: which clocks exist, when signals arrive at the boundary of the chip, which paths are deliberately exempt from timing analysis. The file is text, it looks like configuration, and it is therefore easy to imagine a language model drafting it.

The trouble is what happens when it is wrong. Delete one input delay and nothing breaks. The tool does not crash. It does not warn. It simply stops checking that path, and then it reports a clean result. A design that has never been properly constrained and a design that is genuinely correct both come back looking the same.

The mistake surfaces weeks later at signoff, or in silicon, where it is expensive. This is the property that makes the file worth automating and dangerous to automate carelessly: its failure mode is silence, not error.

02 · The bet

Asking the model to check its own work is not a check.

A model's opinion about its own output is not evidence. It is another sample from the same distribution, with no independent access to the properties that actually matter. So the first repair is obvious: get the verdict from something outside the model.

The second repair is less obvious and is the one this research is really about. Correctness in this domain is not one question. Whether a constraint set is structurally sound and whether the timing it implies actually closes are two different questions, and in practice they are answered by two different deterministic tools with two different catalogs of rules. Collapsing them into one pass or one score destroys the disagreement between them, and that disagreement is information.

So the bet was to keep them apart on purpose, give each one authority over its own property only, and put a separate component in charge of the accept or reject decision. The five phases describe how that is arranged in practice.

03 · How the work was run

Frozen first, interpreted second.

A

Everything that could be frozen was frozen

Task definitions, prompts, model identifiers, retry budgets, timeouts and oracle versions were fixed and hashed before the runs. The tools were pinned to exact versions and executed read only. Nothing in the loop could rewrite a frozen record.

B

Human gates sat between the phases

Each research gate was an explicit checkpoint where a person reviewed the record and approved the next step. Automated tooling produced evidence and analysis. It did not decide what counted as a finding.

C

The non-claims were written before the pressure to state them

The list of things this work does not establish is published alongside the findings, in the same register, because a claim boundary written after the fact tends to be written to fit the result. Read the non-claims.

04 · What had to be given up

Three sentences the record would not support.

The causal sentence. Broader task framing looked better in the pre-registered pilot, and the direction held in all three task blocks. The test still did not reject the null. It is reported as positive in direction and not significant, which is a weaker sentence than the one the author wanted to write.

The equivalence sentence. A larger four-arm benchmark produced an identical reading on its primary metric across every completed run. That is a metric that could not discriminate on that substrate, not a demonstration that the arms were the same. It is published as a metric-power failure, and the stage it was meant to gate never ran.

The priority sentence. Generate then repair loops, language-model constraint generation and model-assisted timing analysis are all established prior art. This work claims none of them. What it claims is the particular separated arrangement and the controlled characterisation of its behaviour.
