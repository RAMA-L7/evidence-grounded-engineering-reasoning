## 3. ODQ-1 — Injection Point

### Decision: TASK CONTEXT → ORACLE FEEDBACK → INSTRUCTION

The C1 prompt follows this exact section ordering:

```
┌─────────────────────────────────────────────┐
│ SECTION 1: TASK CONTEXT                     │
│                                             │
│   design_context (from engineer_visible)    │
│   objective (from engineer_visible)         │
│   constraints (from engineer_visible)       │
├─────────────────────────────────────────────┤
│ SECTION 2: CANDIDATE (Engineer's proposal)  │
│                                             │
│   The SDC candidate generated by the        │
│   Engineer on the first model call.         │
│   (Same as C0 — candidate is present.)      │
├─────────────────────────────────────────────┤
│ SECTION 3: ORACLE TEXT FEEDBACK             │
│                                             │
│   Deterministic text rendered per this      │
│   contract from the EvidenceArtifact.       │
│   (This is the C1 treatment variable.)      │
├─────────────────────────────────────────────┤
│ SECTION 4: INSTRUCTION                      │
│                                             │
│   "Given the oracle feedback above,         │
│    produce a revised SDC candidate.          │
│    Output SDC inside a ```sdc code block."  │
│                                             │
└─────────────────────────────────────────────┘
```

### Rationale

- **Task context appears first** — same as C0, establishing the engineering problem
- **Candidate appears second** — the Engineer sees its own proposal (same as C0 pipeline)
- **Oracle feedback appears third** — after the candidate, so the Engineer can relate findings to its proposal
- **Instruction appears last** — tells the Engineer what to do with the feedback

### What Does NOT Change from C0

- The task context is identical to C0 (design_context, objective, constraints)
- The candidate is produced by the same model in the same way
- The Engineer is the same single probabilistic component

### What Changes

- **C0:** Task context → instruction → [END — Engineer produces candidate]
- **C1:** Task context → candidate → oracle feedback → instruction → [END — Engineer produces revised candidate]

### Candidate Repetition

The candidate IS included in the C1 prompt (Section 2). This is necessary because:
1. The Engineer needs to see what it proposed to relate findings to it
2. The feedback references findings about the candidate — without the candidate visible, the Engineer cannot act on specific findings
3. This matches the natural feedback loop: proposal → evaluation → revision

### Section Labels

Each section is delimited by a clear header. The exact labels are:

```
--- TASK ---
<design_context>
<objective>

--- CANDIDATE ---
```sdc
<candidate_sdc_text>
```

--- ORACLE FEEDBACK ---
<rendered text feedback per this contract>

--- INSTRUCTIONS ---
Given the oracle feedback above, produce a revised SDC candidate.
Output SDC inside a ```sdc code block.
```

### Determinism

The section ordering is frozen. The C1 runner constructs the prompt in exactly this order for every run. No section may be reordered, omitted, or duplicated.

## 4. ODQ-2 — Iteration Protocol

### Decision: SINGLE-SHOT

C1 is **single-shot feedback**. The pipeline is:

```
MODEL (1 call)
  ↓
candidate
  ↓
oracle (1 evaluation)
  ↓
deterministic text feedback
  ↓
FINAL C1 OUTCOME
```

### What This Means

- **One model call** — the Engineer produces one revised candidate
- **One oracle evaluation** — the oracle evaluates the initial candidate
- **One feedback rendering** — the text feedback is rendered once
- **No second model call** — the Engineer does NOT get to iterate
- **No feedback loop** — the Engineer sees feedback but cannot re-propose

### Why Single-Shot

1. **Causal isolation:** C0 is single-proposal. If C1 introduces iteration, it introduces both "text feedback" AND "iterative interaction / additional model calls" as simultaneous changes. That violates the one-variable-at-a-time principle.

2. **Clean comparison:** C0 = one proposal, no feedback. C1 = one proposal, with feedback. The only difference is exposure to feedback.

3. **Protocol §6 definition:** C1 is defined as "+ textual tool feedback." Iteration is not part of the C0→C1 delta.

4. **Budget preservation:** C0 uses 1 model call per task. C1 single-shot also uses 1 model call. No budget change required.

### What C1 Does NOT Introduce

- ❌ No second model call (no revision loop)
- ❌ No oracle re-evaluation after revision
- ❌ No additional feedback rendering
- ❌ No iteration counter
- ❌ No convergence check within C1

### Comparison

| Aspect | C0 | C1 (Single-Shot) |
|--------|----|--------------------|
| Model calls | 1 | 1 |
| Oracle calls | 0 (evaluator-side only) | 1 |
| Feedback | None | Text feedback (this contract) |
| Iteration | None | None |
| Final candidate | First proposal | Revised proposal (after seeing feedback) |

### Budget

C1 remains compatible with MODEL-002's declared budget:
- model_call_limit: 5 (C1 uses 1)
- oracle_call_limit: 5 (C1 uses 1)
- max_iterations: 5 (C1 uses 1)
- max_wall_clock: 300s (C1 uses <5s)

No budget change is required. No REQUIRES EXPERIMENT CHANGE CONTROL.

## 5. ODQ-3 — Line Representation

### Decision: line=0 → `Line: N/A`

In the existing oracle evidence, `location.line = 0` means "no source line available." This is a sentinel value, not a real source location.

### Rendering Rule

| Value | Rendering | Meaning |
|-------|-----------|---------|
| `line > 0` | `(Line N)` | Source line N |
| `line = 0` | `(Line: N/A)` | No source location available |

### Rationale

- `Line: N/A` is semantically honest — it says "location unknown" rather than pretending line 0 is a real location
- It matches the oracle's actual semantics (line 0 = sentinel for "not applicable")
- It does NOT require modifying the oracle — this is purely a rendering decision
- The underlying EvidenceArtifact still carries `location.line = 0` — the rendering is cosmetic

### Consistency

All findings with `line = 0` render as `(Line: N/A)`. This is applied uniformly across all severity levels.

## 7. Deterministic Rendering Rules

### Core Requirement

The same EvidenceArtifact MUST produce the same C1 text feedback, every time.

### Section Order (Frozen)

1. `--- TASK ---` (design_context + objective)
2. `--- CANDIDATE ---` (candidate SDC in code fence)
3. `--- ORACLE FEEDBACK ---` (rendered feedback per this contract)
4. `--- INSTRUCTIONS ---` (revision instruction)

### Feedback Field Order (Frozen)

1. `ORACLE RESULT` header
2. Oracle execution status line
3. (blank line)
4. `EVIDENCE SCOPE` header
5. Scope line
6. Scope limitation line
7. (blank line)
8. `FINDINGS` header
9. Finding lines (sorted per sort algorithm)
10. (blank line — only if findings exist)

### Finding Sort Algorithm (Frozen)

```python
SEVERITY_ORDER = {"error": 0, "warning": 1, "info": 2}

def sort_findings(findings):
    return sorted(findings, key=lambda f: (
        SEVERITY_ORDER.get(f["severity"], 99),
        f["code"],
    ))
```

### Finding Rendering (Frozen)

```
[SEVERITY] CODE: Message (Line: N/A)
```

or, when line > 0:

```
[SEVERITY] CODE: Message (Line: N)
```

Where:
- SEVERITY = uppercase (ERROR / WARNING / INFO)
- CODE = exact finding code
- Message = exact oracle message (no truncation, no paraphrase)
- Line = `N/A` when line=0, `N` when line>0

### Whitespace (Frozen)

- Sections separated by `--- HEADER ---` delimiters
- Blank line between ORACLE RESULT and EVIDENCE SCOPE
- Blank line between EVIDENCE SCOPE and FINDINGS
- No trailing whitespace
- No trailing blank line
- Line endings: `\n`
- No indentation

### Empty Fields (Frozen)

| Scenario | Rendering |
|----------|-----------|
| No findings | `FINDINGS` header present, no lines below |
| ORACLE_FAILURE | Only `ORACLE RESULT` section; no EVIDENCE SCOPE or FINDINGS |
| evidence_scope = null | EVIDENCE SCOPE section omitted |
| line = 0 | `(Line: N/A)` |
